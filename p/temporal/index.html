Limits
  • per-object-cap Payloads: warning at 512 KB and error at 2 MB; a gRPC message is limited to 4 MB source
  • per-object-cap Workflow History: error at 50 MB or 51,200 Events, which terminates the Workflow Execution source
The open source Temporal Service has a default limit of 2,000 pending Activities, Child Workflows, Signals or Workflow cancellation requests, which the dynamic configuration overrides.
Bindingnone The documentation states no quota for the open-source server; the Persistence and Visibility stores and the machines that the user runs bound throughput, and the per-Workflow-Execution limits are defaults in the server.
Identityanonymous No account with Temporal is needed: the open-source quickstart installs the temporal CLI (brew install temporal) and runs temporal server start-dev on the local machine, and a credit card is required only to sign up for Temporal Cloud.
Egressnot set by the software: Workers and clients connect to the user's own Temporal Service, so the network terms of the host that runs it apply
Per-object capPayloads (the Workflow context and each Workflow and Activity argument and return value): Temporal warns at 512 KB and errors at 2 MB; a gRPC message is limited to 4 MB
Retentionclosed Workflow Execution histories are kept for the Namespace's Retention Period, which is at least 1 day and defaults to 3 days when a Namespace is created with the temporal CLI and no value (3 days)
Interfacerest, cli the Frontend Service exposes a gRPC Proto API on port 7233 that the Temporal SDKs use (the vocabulary has no gRPC term); an HTTP API is switched on in the server's static configuration (httpPort, 7243 in the Nexus example) and on the development server with --http-port; the temporal CLI interacts with the running server, and the development server serves the Web UI at port 8233
Toolingthe user installs and runs the Temporal server on a rented or free machine: temporal server start-dev from the temporal CLI (a single binary with no external dependencies), the Docker Compose example (PostgreSQL and Elasticsearch), the Temporal Server and UI Server Go binaries, or the Helm charts on Kubernetes; the Temporal SDKs (Go, Java, Python, TypeScript, .NET, Ruby, PHP) and the temporal CLI.
Composes withLast resort after the hosted durable-execution offers (the hosted Inngest free tier in dev-services/inngest, and Temporal Cloud in dev-services/temporal-cloud): the user's own Workers connect to a Temporal Service that the user installs and keeps running.
ReliabilityThe development server is not intended for production use, skips certain HTTP security checks, and loses Workflow Executions when its process dies unless --db-filename sets a persistent store. A production Temporal Service needs data stores for persistence that the user creates and maintains, has no role-based access control or audit logging out of the box, and its hosts should not be accessible from the public internet; Temporal does not guarantee support for the server.
NotesSelf-hosted software and the last resort: the hosted offers come first (dev-services/temporal-cloud, and the hosted Inngest free tier dev-services/inngest). This record is no duplicate of dev-services/temporal-cloud: it is the open-source server that the user installs and runs.
