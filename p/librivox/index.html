Bindingper-ip-shaping The API is metadata and would take minutes to walk at 500 records a request; the bytes come from archive.org, so the Internet Archive's per-IP ceiling is what decides a TiB-scale pull.
Identityanonymous No key and no account: the API answered an anonymous GET with 200 and 3,084 bytes for limit=2.
EgressMetadata is free and unmetered from the API. The audio is not served by librivox.org: each record's url_zip_file points at archive.org/compress/<item>/..., so audio bytes are Internet Archive egress and inherit its per-IP shaping.
free allowance: no byte allowance published
Per-object capnot applicable: one MP3 per section, one ZIP per book. The ZIP is served by archive.org, so the object size is the Internet Archive item's size.
Retentionpermanent: public-domain recordings 'donated to the public domain', with the audio stored as Internet Archive items
Interfacerest, cli GET https://librivox.org/api/feed/audiobooks with id, since, author, title, genre, fields, extended, coverart, limit, offset, format, sort_order. Parameters may be path segments instead of query strings.
endpoint: https://librivox.org/api/feed/audiobooks?format=json&limit=500&offset=0
Toolingcurl/python-requests; any HTTP client. No SDK and no rclone backend is needed because the metadata is a plain JSON API and the audio is a plain archive.org URL.
Composes withHarvest the catalogue through the API (a few hundred requests), then pull the MP3s from archive.org - the same egress path and the same shaping as any other Internet Archive item.
ReliabilityThe API changed in 2026-09-26 to cap limit at 500; older clients that asked for more are silently clamped rather than rejected.
NotesThe interesting part is where the bytes are not: librivox.org serves a small JSON catalogue and archive.org serves the audio. A plan that expects a fast audiobook mirror from this API alone will move metadata and no media.
Evidence notedocumented The API contract is the vendor's own page and was exercised here for two records; the audio path is read from the record's url_zip_file field, not downloaded. Downloading one ZIP would raise it.
