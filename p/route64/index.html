ToolingAn account in the self-service manager portal is the only published route to an allocation. The address then has to be bound to an existing endpoint, either by placing compute at one of the vendor's PoPs or by terminating one of the six published protocols from it: GRE, GRETAP, SIT, WireGuard, L2TPv3, VXLAN, all listed with both IPv4 and IPv6 endpoints. No proxy wrapper, API client, downloadable configuration or test address is published for the static-IP product, so the announcing AS and the registration class cannot be checked before signing up. A missing wrapper is not a reason to reject this provider: what is missing here is the protocol and the test address, not the wrapper.
Composes withIt supplies the Workers gateway with IPv4 source addresses in an ASN that is not AS13335, which is the rung-4 move, and it needs an existing compute endpoint to terminate a tunnel from or to sit at a PoP; it adds address count and one ASN, not registration-class diversity, because every address in the five blocks is IPXO-registered.
ReliabilityBest effort with no SLA ('This is a free best effort service. You have no service levels or guarantees.'); all five blocks are one IPXO registration class and one announcing AS, so a prefix-level blocklist entry or a nullroute removes all 1,280 addresses together.
NotesRoute64 makes no class claim at all, so the class is settled entirely by the registry, and the registry does not support one: four blocks read IPXO or IPXO-LEASED as SUB-ALLOCATED PA or ASSIGNED PA, country EU, registrant ORG-PC1552-RIPE, with PC21176-RIPE 'Private Customer' as admin, tech and abuse contact and the remark 'End User Organization'. A sub-allocation of a lease broker's PA space is a broker's pool, not an eyeball broadband network, so rung 5 is not cleared. (2) That the announcement and the registration disagree, which is the topic's warning stated as a claim. Confirmed, and precisely: the announcement is Route64's own, since RIPE autnum 212895 is registered as ROUTE64_ORG and all five /24s are originated there and visible to 268 or 269 of 269 RIS peers, while the registration belongs to IPXO on four blocks and to an ARIN 'Private Customer' assignment on the fifth. Two parties, neither of them an ISP. That is a rung-5 failure, and it is not a rung-3 or rung-4 failure: the addresses are in five different /24s and in an ASN that is not AS13335, so both of those rungs are cleared by the measured announcement. (3) That the vendor's own block count can be relied on. Refuted: the page says 'Our address portfolio includes 3 IPv4 /24 blocks' and RIPEstat returned five, so the pool to draw from is 1,280 addresses rather than 768. That changes the size of the caveat, not its direction. A fourth finding belongs in the record rather than the notes: the vendor publishes a geofeed that carves single /24s into per-country fragments, a /28 in Stockholm, a /29 in London, /31s in Paris, Zurich and Frankfurt. A geofeed-aware upstream will read the declared country while RDAP still says EU, so the declared location is a vendor artifact and neither a registry fact nor a class. Every fact about the network rests on one read, on 2026-10-24: one announced-prefixes query, five routing-status queries, five RDAP queries, one geofeed fetch and two vendor pages. Nothing was delivered and nothing was echoed, and the instruction that matters for this record is that one delivered address must be measured before the class is relied on. That measurement is not here: it needs an account, an allocation, an echo service and a control request from a Cloudflare address in the same minute, and without it this record reports what the registry says rather than what an address does. This record does not duplicate egress/route64-org, which owns the free IPv6 /56 WireGuard tunnel and was read on 2026-10-23; this record owns the IPv4 static allocation only. Nothing in that record is corrected here, and the 200 Mbit/s design point and the provider sentences appear in both because they bind both products, each citing the provider directly.
