Toolingsnapcraft upload / snapcraft push (the write path), Snap Store API v2 (api.snapcraft.io/v2/snaps/info/<name> with header Snap-Device-Series: 16) for metadata, and plain HTTPS GET of the channel-map download.url for bytes. No rclone backend; a wrapper would have to speak the snapcraft upload protocol to push.
Composes withunlimited snaps per publisher account x unlimited revisions per snap (revision history is retained server-side - the forum thread discusses 3 GB across 3 revisions of a 1 GB game). Multiply by unlimited free Ubuntu One accounts. Realistically ~1.6 GB x N revisions x N snaps, but upload reliability degrades well before 5 GB.
ReliabilityThe write path is the weak link, not storage: multi-GB uploads fail with opaque HTTP 500 ('timeout in the object storage load balancers') and with client-side 'Data queue size is too large'. Bytes are served perfectly once published (200 77574144 application/octet-stream verified). Snaps are squashfs images - arbitrary content must be packaged into a snap with a valid snapcraft.yaml, so this is a wrapper-only route.
