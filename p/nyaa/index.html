The feed is the whole interface: no key, no token, no pagination wall on the routes tried.
Bindingrequest-rate No byte accounting exists on an index; polling a saved search is a handful of requests a day, far below anything that would throttle.
Identityanonymous No account for search or RSS; uploading and commenting need one, which is not needed here.
Egressno byte allowance: the feed serves XML and .torrent links; the transfer is client-to-swarm
free allowance: none published
Per-object capthe tracker caps a single torrent file and the site caps uploads, neither of which is a client-side limit on the index
Retentionreleases persist; the feed returns only the query's matches, so age is not implied by the feed
Interfacerest RSS at /?page=rss with the usual query parameters (q, c, f); each item's <link> is a .torrent download and <guid> is the view page.
endpoint: https://nyaa.si/?page=rss&q=ubuntu&c=0_0&f=0
ToolingAny RSS reader; the item link is already the .torrent, so no page fetch is needed.
Composes withA saved search as an RSS feed is the cheapest possible subscription: one URL per interest is polled and returns .torrent links, which a debrid service then turns into cached playback.
ReliabilityA query with no match returns a valid feed with zero items rather than an error, so a client must check item count rather than status. The one match for 'ubuntu' was dated 2009, so the index holds very old items and a fresh-looking feed says nothing about freshness.
NotesThe narrowest and most reliable feed in the sector: a saved search is a URL, and the URL returns.torrent files. Useless outside anime and East Asian media, which is why it is a second feed rather than the primary one.
Evidence notedocumented The feed was fetched on 2026-10-23 and parsed: one item for 'ubuntu', with a .torrent link. A month of polling would raise it to measured.
