Free tierNo published byte quota on the /data volume. The docs state only 'Files written to /data persist between requests, across runner restarts, and across deployments' and 'Files you write there persist until you delete them. Runner shutdown does not delete these files.' Capacity is bounded only by what you pay to keep a runner alive; there is no free storage allowance and no documented ceiling.
unit none; metered on stored-bytes
Pricenone stated
Limits
  • per-object-cap (binding) 100 GB per file source
  • write-gated approval (request at fal source
Per-object-cap is upload-method-dependent (this is the useful part): fal files upload CLI ~100 GB per file (10 MB parts, max 10,000 parts); dashboard drag-and-drop 1 GB; upload-from-URL 5 GB and must complete in 10 minutes; POST /serverless/files/file/local/{path} ~4.5 MB per request; writes from inside a running app are exempt ('Not subject to these limits. The runner writes straight to the volume'). Retention: indefinite, self-managed. Billing: you are billed per second for every runner state except PENDING, DOCKER_PULL and TERMINATED. SETUP and IDLE are both billed, so holding storage open costs GPU-time.
Identityemail (placeholder) not published
EgressNOT free and NOT anonymous: '/data' files are 'not URL-accessible'. There is no public download URL, so the egress question does not arise. Bulk in/out is via fal files CLI or the REST storage API.
Per-object cap100 GB per file (100000000000 bytes)
RetentionNo published byte quota on the /data volume. The docs state only 'Files written to /data persist between requests, across runner restarts, and across deployments' and 'Files you write there persist until you delete them.
Interfacerest, cli rest
Toolingfal Python CLI (fal files upload/download/list/remove), @fal-ai/client JS storage API, fal.download_file(url, target_dir='/data/...') in-app. Chunked at 4 MB into a global object store; parallel reads hit a distributed cache (docs claim 6-8 GB/s distributed, 10-15 GB/s local NVMe).
Composes withStorage is tied to paid compute workloads rather than standalone storage. Serverless deployments require approved account access and compute runtime fees apply.
ReliabilityServerless access is gated by per-account approval (request at fal.ai/dashboard/serverless-get-started), so this is not a self-serve multiplier. Docs warn that streaming a multi-GB artifact in small chunks to /data is much slower than one bulk copy.
