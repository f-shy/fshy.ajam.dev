Free tierEach record comes with a default quota of 50 GB and an unlimited number of records may be uploaded under 50 GB; a further 150 GB additional allowance is held per account and can be distributed across records as needed.
unit GB; metered on stored-bytes; CERN funds the service, so the quota is a policy that can move; it is not a purchased allowance with a contract behind it.
Pricenone stated
Limits
  • per-object-cap 50 GB per record, and 150 GB total per account source
  • write-gated (binding) a DOI is minted on publish and the record is then immutable except for metadata; files may only be added in a 30-day window source
Two constraints bind: individual depositions are capped at 50 GB, and published records cannot be modified in place. Additional content requires creating new depositions with distinct DOIs.
Bindingwrite-gated The cap is generous for the shard sizes; the gate is what decides the workflow, because a mistake after publication cannot be corrected in place, only superseded by a new version.
Identityemail A local account asks for a username, full name, affiliation, email address and password, and the email must be confirmed before the first upload; ORCID and GitHub logins are offered as alternatives and neither is required. No card and no institutional check.
Egressfree with no metered allowance; the published limits are on request count, not on transferred bytes: a guest may make 60 requests per minute, an authenticated user 100; files are served to an anonymous ranged GET without authentication.
Per-object cap50 GB per record (50000000000 bytes)
RetentionItems are retained for the lifetime of the repository, currently the lifetime of the host laboratory CERN, whose experimental programme is defined for the next 20 years at least; a withdrawn record leaves a tombstone page and the DOI and URL of the original object are retained.
Interfacerest, s3-compatible REST deposit API with a token, plus an S3-compatible endpoint for large files. Not a WebDAV or rclone-native backend.
endpoint: https://zenodo.org/api
Toolingrequests or curl against the deposit API; the S3 endpoint needs a generated key pair
Composes withThe useful chain is write-once archive plus a parallel ranged reader: Zenodo holds the durable copy and a Worker or a ranged client serves it, because a single stream is slow but many streams are not.
ReliabilityCERN-operated and long-lived; the failure mode is policy change rather than downtime. Records are immutable after publication, so a quota reduction would affect new deposits and not existing ones. The binding limit on reading is the per-connection throttle, which parallel ranged GETs defeat; see zenodo-anonymous-download-throughput.
NotesSplit across three sub-finding records that each answer one question: anonymous download throughput, DOI batching, and restricted-access records as working storage. This record is the provider itself, so that a document citing Zenodo has one canonical target.

Free tierOne DOI per record, automatically, free, and unlimited records. DOI count is therefore not a constraint on sharding: a 410-record archive is also 410 citable handles at no extra cost
unit objects; metered on object-count; Documents the Digital Object Identifier assignment mechanism for multi-part dataset partitioning.
Pricenone stated
Limits
  • request-rate (binding) 100 requests per minute authenticated, 30 per minute on the search API, which sets the batch size per hour rather than any record count cap source
  • retention-clamped a DOI is revoked if the record is deleted inside the 30-day window, and tombstones after that source
Content outside the repository's scope is removed and its DOI revoked, which is the only stated ground for losing an identifier after the 30-day window
Bindingrequest-rate Nothing limits the number of DOIs. What limits a batch job is the authenticated request rate, so the practical ceiling is records per hour and not records per account
Identityemail an email address, GitHub or ORCID account. No institution is needed to mint a DOI, which is the unusual part
EgressNot applicable to the identifier itself. Retrieval of the deposited bytes is free and unmetered, and the read path is measured in the sibling record
Per-object capOne DOI per record, and the deposition response carries a reserved DOI already set through prereserve_doi, so a batch job gets a citable handle without a separate call
RetentionDOIs are permanent and cannot be reused or reassigned. Deleting a record within 30 days revokes the DOI, after which it tombstones. A record cannot be un-published to reclaim the identifier
Interfacerest POST /api/deposit/depositions returns a record with a reserved DOI already set, so one call per record yields one identifier
Toolingany HTTP client. zenodo_get and zenodo-cli both wrap the same API for the read side; there is no rclone backend
Composes withBecause every record gets a DOI for free, a 410-record archive is also 410 citable handles with zero extra work. This is the mechanism that makes the unlimited-records story practical rather than merely permitted: there is no per-DOI cost and no approval step, so the archive can be sharded to the record boundary and every shard stays citable
ReliabilityBatch-creating hundreds of records is API-rate-bound only and not quota-bound, so the operational risk is a batch that half-completes and leaves Pending files rather than one that hits a ceiling
NotesZenodo dataset publishing assigns unique DOIs via DataCite. Individual datasets are capped at 50 GB per deposition, and automated DOI minting enables programmatic dataset sharding across multiple depositions.

Metadata is always public even when the files are restricted, so titles, descriptions and the minted DOI leak. That is a property of the visibility model and not a defect in this record
Bindingper-object-cap The quota and the visibility are independent, so restricting a record buys privacy and no capacity.
Identityemail an email address, GitHub or ORCID account. Restricting a record requires no additional verification.
EgressFree. A secret link grants 'Can view' on restricted or embargoed files of all current and future versions of that record, with optional expiry
Per-object cap50 GB per record on the default quota, with the 150 GB account pool distributable across records, and a hard 100 files per record (50000000000 bytes)
RetentionA record cannot be deleted after 30 days. Restricted records carry the same rule, so a restricted record is as permanent as a public one and its quota is consumed monotonically
Interfacerest the same deposition API; visibility is a field on the draft, set to restricted with an embargo date or a share link, and share links are managed from the record's Links tab
Toolingany HTTP client for the deposition and file APIs, working in the same way as the public path. There is no rclone backend, so uploads are plain HTTP PUT against a bucket URL
Composes withThis is what turns Zenodo from a cold archive into something usable as a hot working set: data can be kept off the public index while still holding 50 GB times N, and still read it programmatically with a token or a shared link. It composes with the 32-connection parallel read measured on the public path, because the throttle is per connection and not per visibility
ReliabilityAnswers the working-storage question: workable for private data, but every record still carries permanently public metadata and a DOI, so it is a leaky private tier and not a private bucket. An interrupted upload leaves a Pending file that must be removed by hand
NotesZenodo supports restricted-access records with secret sharing links alongside public records. Storage quota is 50 GB per deposition with identical API upload endpoints and lifecycle terms.
